# P2 — independent Gentoo systemd guest

P1 remains the installer medium. P2 creates a separate installed system, with its own kernel, modules, dracut initramfs, GRUB UEFI fallback loader, ext4 root and FAT32 ESP. It is not yet the custom Live ISO milestone.

## Commands and authorization boundary

```bash
# Host prerequisites only; no virtual disk changes.
python3 scripts/p2_vm.py diagnose

# New independent 64 GiB QCOW2 plus byte-identical full-file checkpoint.
python3 scripts/p2_vm.py prepare \
  --live-iso /home/williandias/G15Forge-VM/iso/g15forge-prototype-v0.1.iso \
  --stage3 /home/williandias/Downloads/G15Forge-Gentoo-Stage3-v0.4/artifacts/stage3/stage3-amd64-systemd-20261018T124555Z.tar.xz

# Use the exact lab path returned by prepare.
python3 scripts/p2_vm.py diagnose --lab EXACT_LAB
python3 scripts/p2_vm.py review --lab EXACT_LAB
```

The guest diagnostic attaches the new QCOW2 **read-only**, uses independent OVMF NVRAM, no network, the existing installer ISO and a new read-only seed CD. It checks the actual QMP block graph before typing any guest command. Guest identity checks require UEFI, live-root command line, exactly one disk, `/dev/vda`, its unique virtio serial and 64 GiB capacity. Diagnostic output lists available tools, disks and live mounts. It powers the guest off without partitioning.

The disk and NVRAM template checkpoints are separate regular files with hashes and read-only owner permissions. Phase records are created exclusively, flushed and fsynced along with their containing directory. The virtio serial comes directly from `/sys/class/block/vda/serial`; the stock live guest's offline udev database left the lsblk SERIAL column empty, which is covered by a regression test.

The immutable review records disk/checkpoint paths, device/inode identities, lengths, modes, hashes, script hashes, successful diagnostic evidence, intended layout and the exact future QEMU command. **Stop here for specific human confirmation.** The Python CLI and an approval JSON do not create native authorization. A recorded approval is documentary and must correspond to the user's explicit confirmation and applicable runtime approval.

After that confirmation only, record an approval JSON with exactly these fields, bound to the actual review:

```json
{
  "approved": true,
  "operation": "partition-and-format",
  "lab_id": "EXACT_LAB_ID",
  "serial": "EXACT_VIRTIO_SERIAL",
  "review_sha256": "EXACT_REVIEW_SHA256"
}
```

Then the separately gated commands are:

```bash
python3 scripts/p2_vm.py partition --lab EXACT_LAB --approval EXACT_LAB/approval.json
python3 scripts/p2_vm.py install --lab EXACT_LAB
python3 scripts/p2_vm.py verify --lab EXACT_LAB
```

`partition` is single use: it requires the untouched checkpoint match, current file identities, unchanged scripts, exact review/approval binding and no previous completion receipt. Guest guards run again before GPT/format commands. A failed attempt remains preserved; no automatic rollback, restoration, reformat or retry is performed. Installation also refuses an existing Gentoo tree instead of silently overwriting a partial target. Source/script changes require a fresh reviewed lab under this initial conservative controller.

## Installation recipe

The concrete partition/format commands are versioned in `guest/p2-installer.sh`, under the `prepare` branch: GPT with a 1 GiB EFI System Partition and ext4 root in the remaining space. Only the uniquely identified `/dev/vda` is accepted. The seed approval is absent from diagnostic runs.

`install` requires a successful partition receipt. Only this phase enables QEMU user-mode NAT (no bridge, tap or port forwarding). The guest obtains DHCP, verifies Stage3 against `01ed7040d5768b5a056d3c0f7d38b0db23e8c1c4e28a57736d92ea9e30342217`, extracts it inside the ext4 target and configures:

- The Stage3's `default/linux/amd64/23.0/systemd` profile; signed webrsync repository updates and mandatory binary package signature verification.
- Generic x86-64 upstream binhost, conservative build concurrency, hostname `g15forge-p2`, en_US.UTF-8, America/Sao_Paulo, UUID-based fstab and systemd-networkd/resolved.
- Gentoo distribution binary kernel and modules, dracut generic initramfs with virtio storage/network and Intel microcode files.
- GRUB x86_64 UEFI removable fallback, without writing firmware NVRAM entries; serial kernel console and a guest-only systemd verification service.

Packages come through [Gentoo's signed binary package mechanism](https://devmanual.gentoo.org/eclass-reference/make.conf/index.html); the [kernel installation model](https://wiki.gentoo.org/wiki/Handbook:Parts/Installation/Kernel/en) follows Gentoo's distribution-kernel guidance. No signature check is disabled, and unavailable signed binaries cause failure rather than an unreviewed source-build fallback. Package versions and Portage information are captured in the installed guest logs; exact future package availability is an external dependency, not a byte-reproducibility claim.

## Independent boot acceptance

`verify` requires the successful installation receipt. Its QEMU graph contains **only the new disk and OVMF firmware/NVRAM**, with no live ISO, seed CD or network. The installed verification service requires PID 1 systemd, UEFI, matching root/ESP UUIDs, ext4/vfat mounts, no ISO filesystem, active essential services, valid boot file hashes, the running kernel's own files and no failed units. It captures mounts, block inventory and boot journal through the serial port, then requests clean poweroff. Success also requires natural QEMU termination and process collection.

Every run preserves its argument list, QMP block graph, seed manifest, serial log, screenshots and result JSON. A timeout, forced termination or absent guest success marker is a failure. Historical QCOW2 images and physical drives are never part of the graph. A host controller lock plus QEMU's native image locking prevent cooperating runs from overlapping; static records alone are not proof of exclusive system-wide authority.

## Validation status before partition approval

P2 code and guard tests are implemented. Synthetic/unit tests do not prove installation, kernel boot or PID 1 systemd. The real P2 disk may be created/checkpointed and diagnosed read-only before approval; **partitioning, formatting, installation and independent boot remain NOT EXECUTED until their corresponding operations actually run**. No P1 build or certification is repeated here.
